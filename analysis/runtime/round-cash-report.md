# Local KourStrike round-start cash

The shipped native maximum is **14,000**. `SearchAndDestroyManager.set_money` (metadata32736, function74498, table20426) clamps decoded money to `[0,14000]` before re-encoding it and updating UI. The cap constants are at WASM offsets23689441 and23689460. Money is a20-byte `ObscuredInt`; direct plaintext memory writes are incorrect.

`SearchAndDestroyManager.OnStateChanged` (metadata32762, function74503, table20452) handles BuyPhase=1. It preserves prior/current state at offsets23691036..23691053, and compares new state with the previous state at23691070..23691075 before state dispatch. The buy branch initializes the buy UI, respawns the player, adds a default1400 or the round's supplied extra-money value, converts the result to `ObscuredInt`, then calls the ordinary money setter. Repeated callbacks for the same state skip this branch.

The minimal seven-byte replacement at absolute offset **23693680** changes `call52777; local.get5; i32.add` (`10a99c0320056a`) to `drop; drop; i32.const14000; nop` (`1a1a41b0ed0001`). The two drops consume the pending input-struct pointer and MethodInfo argument, retaining the lower output pointer. Existing integer-to-ObscuredInt conversion at23693689 and money setter at23693730 remain active. Apply only to the local offline KourStrike served variant, with source hash and expected-byte guards from `round-cash-patch-contract.json`.

This refills cash on first and subsequent BuyPhase transitions. Purchases still deduct cash because the global money setter and purchase code are unchanged. `Start`'s initial0 is intentionally untouched; initialization is not a round-start event. The replacement keeps file/body lengths and table mappings intact. Full original module plus this replacement passed native Node `WebAssembly.validate`; gameplay behavior requires the parent's runtime test.

Its body constructs native round results and calls `SetGameState` with RoundEnd=4 at23705059. Invoke on the live manager during ActionPhase=2 in the local offline room; allow the existing lifecycle to start the next round. Manager instance lookup is `read32(read32(read32(6910428)+92)+20)`. This invokes round rules instead of writing cash. Inspect `round-cash-end-round.json` for complete body and `round-cash-static.json` for the cash/setter/start bodies.
